## Scope and method

The audit traversed the current Core `yuheng-module-system/.../service` and `yuheng-module-infra/.../service` trees, limited to `*ServiceImpl.java`. It indexed each method body containing a direct call whose receiver name ends in `Mapper` or `DAO` and whose method name begins with `insert`, `update`, `delete`, `save`, or `remove`. For each match it records the Core-relative source file, method, declaration line, write calls, and immediately preceding transaction annotation in `core-system-infra-write-methods.csv`.

The index contains 188 write-bearing methods. Twenty-four method entries have a direct `@Transactional` or `@DSTransactional` declaration; 164 do not. This is a source navigation index, not a correctness verdict or coverage metric. It does not infer annotations from class/interface inheritance, follow calls into private helpers, inspect SQL hidden behind helper methods, classify read-modify-write behavior, prove Spring proxy interception, or inspect external side effects. The earlier 162-method count came from a narrower scan and is not directly comparable.

## File storage and Quartz failure-path source review (2026-11-18)

Current Core source confirms that `FileServiceImpl.createFile(byte[], ...)` validates the input, calls `FileClient.upload`, then inserts the `infra_file` metadata row, with no transaction around those operations. `DBFileClient.upload` inserts `infra_file_content` before returning, so a later metadata insert failure leaves content without a corresponding metadata row. Local, FTP, SFTP and S3 clients complete their external write before metadata insertion, so the same failure ordering can leave an external object. `deleteFile` deletes the object/content before soft-deleting metadata; `deleteFileList` deletes each object/content sequentially and only then soft-deletes all metadata. A later storage or database failure can therefore leave missing objects with active metadata, or a partially deleted object set with all metadata still active. These are source-derived failure states; this run did not inject them.

`JobServiceImpl` create/update/status/delete/list-delete and `syncJob` call `SchedulerManager` within ordinary Spring database transactions. The Demo local/dev profiles configure Quartz's `LocalDataSourceJobStore` and do not define a separate non-transactional Quartz data source. Spring's `LocalDataSourceJobStore` obtains its transactional connection through `DataSourceUtils.doGetConnection`; Spring Boot's SchedulerFactoryBean supplies the application data source. Along with the InnoDB engines observed for `infra_job` and Quartz tables, this is source evidence that Quartz JDBC changes can join the current Spring transaction. It supports rollback participation for local/dev database operations, but runtime wiring and failure behavior for each Scheduler operation remain untested. No Quartz failure result is counted in this section.

Runtime injection is blocked in the current environment: the available MySQL principal has grants only on `yuheng_demo.*`, and the container root account login failed. `yuheng_demo` was confirmed to exist with 150 tables; `infra_file`, `infra_file_content`, `infra_job`, `qrtz_job_details`, and `qrtz_triggers` use InnoDB.
